# Events (AsyncAPI) — review guide

Status: **as built, 2026-10-19** (completion round: publish and versions, used-by, external references, in-app leave guard, contacts editing; then the **AsyncAPI importer** and **local JSON validation**; then the reserved-names guard and a hardening pass on the example generator and the editor's patterns). This is the map for reviewing the Events work: what it is, how to run it, the order in which to read the code, which decisions shaped it, and what is not done. Design history lives in `docs/superpowers/specs/2026-10-15-events-self-contained-design.md` (decisions E1–E9) and the plans in `docs/superpowers/plans/` (`2026-10-16-events-completion.md`, then `2026-10-16-events-import-and-json-validation.md`, the latest).

## 1. What this is

An **Event** is one asset: an AsyncAPI 3 document edited in a visual builder. Servers, channels, messages (with payload entity), operations and message properties ("traits") live **inside** the event; there are no separate Message / Channel / Event Spec assets any more.

- **New Event** is the only event entry in the product's *New* menu. Events are listed flat on the product page.
- **Builder** (Design tab): vertical outline — Metadata, Servers, Channels, Messages, Operations, Message properties (Trait), Advanced. Every AsyncAPI 3.0 property is a ready-made, labelled field (generated from `@asyncapi/specs`, coverage is tested). Identifiers (keys) are generated and hidden behind a collapsed "Identifier".
- **Payload format**: a message picks an entity and a *Representation* — **Auto** (the entity's recorded source format, else the protocol default: Kafka → Avro, anything else → JSON Schema) or an explicit Avro / JSON Schema / Protobuf. The form says what Auto resolved to and why.
- **Message properties (Trait)**: reusable property sets. **Built in**: CloudEvents 1.0 and W3C Trace Context (created for every tenant, read-only everywhere, properties shown in the UI). **Library**: Tenant/Domain traits. **Local**: defined in the event with a Properties table. Added from one **+ Add** (applies to Message | Operation).
- **External references**: Channels and Messages each have a "from another event" card. A three-step picker (search published events of the tenant → pick a version, newest preselected → pick the channel or message) adds a reference pinned to **one published version**; the event itself is never offered. Each reference shows its source event, version and item, a status line ("v1.0 → v2.0 available", major called out) and **Update** / **Remove**. Update is always manual and is refused when an operation uses an item the latest version no longer has; Remove shows the impact first. Operations can use external channels and messages (marked "(external)").
- **Right panel**: the AsyncAPI document as live YAML/JSON (CodeMirror 6): instant from the unsaved draft, then enriched with real payload schemas from the server. The **Docs** tab renders the documentation.
- **Publish, Versions, Used by**: the header **Publish** button (enabled for a saved draft without problems) opens the shared raise-only dialog: the suggested bump, a lower one refused, every blocker listed once. **Publish cuts from the saved draft only.** The **Versions** tab lists the published versions, newest first, and shows the stored AsyncAPI document of the one you press **View** on, read-only as YAML or JSON (`?tab=versions&version=<label>`). **Used by** lists the events whose external references point at this one (draft and published references; the list is cut at 50 and says so).
- **Leaving with unsaved edits**: a dialog (*Save & leave / Discard & leave / Stay*) appears for link clicks, explorer rows, the command palette, the new-entity shortcut, the notification centre and the browser Back button; tab/section/item switches inside the page never prompt. Closing the tab or reloading still uses the browser's own warning.
- **Product**: Engineering Lead, Manager and Team emails (`email` or `Name <email>`) on *Create New Product* and, afterwards, **Edit contacts** on the product page.
- **Import existing…** (New Event dialog): paste or upload an **AsyncAPI 3.0** document (YAML or JSON, up to 1 MiB; 800,000 bytes in the browser because of the server-action body limit). A **Preview** step shows what will be created (counts, the entities, the built-in traits used, warnings) and **Import** creates it. Each payload schema becomes a **draft entity** in the product, with its pin left **unpinned**: publish the entities and pin their published versions in the builder before the event itself can publish. CloudEvents / W3C Trace Context traits map to the tenant's built-in traits; a name that is taken gets a numeric suffix and a warning; a payload the importers cannot read becomes a placeholder entity and a warning. An external `$ref` is refused (no network access); there is no "import from URL".
- **JSON validation** (builder): message **example payload / headers** are checked against the pinned entity's JSON Schema, with a **Generate from payload** button (openapi-sampler); the 24 raw-JSON **binding** fields are checked against the AsyncAPI binding schemas. Both use `codemirror-json-schema` (loaded lazily, only when a schema exists) and show **warnings, never blockers**: Save and Publish are not gated by them.
- **Reserved names**: `hasOwnProperty` and `__proto__` cannot be used as an event key, a field name or an entity / enum / scalar / union / API / trait / event name, because the AsyncAPI parser we use crashes on them and published versions cannot be corrected later (a plain message at the field, one guard before the parser at publish, nothing crashes or leaks a stack trace). Decision, enforcement points and how to lift it: §5.
- **Bounded parser**: the AsyncAPI parser (used by publish, the live Code panel's checks and the importer) and the importer's YAML/JSON read run in warm **child processes** with a hard time limit (validate 15 s, read 4 s), so a hostile or enormous document costs one killed worker and a clear "too complex" message instead of blocking the server. Operation notes (build step, pool size, memory, standalone shipping): §5 and gap 1.
- **Not built**: see §6.

## 2. Run it

```bash
npm run db:deploy            # applies migrations (also installs the built-in traits for every tenant)
npm run db:seed-events-demo  # idempotent demo data: Payments/Checkout + Risk/Fraud, entities, events incl. the showcase `order-platform`
npm run dev                  # http://localhost:3000 — Payments → Checkout → Events
```

In a **git worktree** with a symlinked `node_modules`, Turbopack refuses to start; use `npx next build --webpack` then `AUTH_TRUST_HOST=true npx next start -p 3000` (`next start` needs the trusted-host flag or logins bounce). In a normal checkout none of this applies.

## 4. Tests

- Unit + integration: `npx vitest run tests/unit tests/integration` (integration uses the dev PostgreSQL from `.env`; tests use unique names and clean up).
- Browser: `npx playwright test` runs the whole suite as two Playwright projects: **`chromium`** (every spec except two, in parallel) and **`serial-after`** (`navigation.spec.ts` and `events-external-refs.spec.ts`, one worker, started only after `chromium` has finished: the navigation spec crawls every explorer node of the shared database and the external-references flow runs the real TypeSpec CLI, so both flaked when other specs created and deleted data beside them). The app must be on :3000 with the seeded admin (see `tests/e2e/helpers`). A spec of `serial-after` pulls in the whole `chromium` project first unless you pass `--no-deps` (`npx playwright test tests/e2e/navigation.spec.ts --no-deps`); a spec of `chromium` runs alone as usual (`npx playwright test tests/e2e/events-import.spec.ts`). If any `chromium` test fails, Playwright reports the two serial specs as "did not run": rerun them with `npm run test:e2e:serial`. The events specs are `events-builder`, `events-publish`, `events-external-refs`, `events-leave-guard`, `events-import`, `events-example-validation`, plus `product-contacts`, `navigation` and `dashboard-not-found`. `events-leave-guard` is Chromium-only (it relies on the Navigation API for the Back button). The publish and external-reference specs use the real TypeSpec CLI and are slow under load; the external-references spec waits up to 90 s for the publish preview.
- Importer and validation: `npx vitest run tests/unit/lib/events tests/unit/services/events tests/unit/components/events` (includes the 48-row worst-case matrix, the fixtures in `tests/fixtures/asyncapi-import/`, the CodeMirror boundary test and the stale-file test for the generated binding schemas); `tests/integration/services/events/asyncapi-import.service.test.ts` runs the real service against the dev database (it creates and removes its own data). The generated binding schemas are rebuilt with `scripts/generate-asyncapi-templates.ts`. Reserved names: `tests/unit/lib/event-specs/parser-unsafe-keys-sweep.test.ts` runs EVERY `Object.prototype` name through the real AsyncAPI parser in about ten positions and asserts the set that crashes it equals `PARSER_UNSAFE_KEYS` (it goes red when a parser upgrade changes that set: see §5); `tests/integration/services/events/event-emit-reserved-field.test.ts` proves the real emit and publish refuse a reserved field and a reserved entity name with a readable message and no stack trace.
- DB migrations on PGlite (no server needed): `tests/integration/db/*-pglite.test.ts`, including the guard migration (clean DB passes; every legacy-row case raises).
- Test baseline (2026-10-19): the unit and integration suites pass in full (the old failures of `db-emitter-parity` x4, `schemas-tab` x3 and `e2e-critical-flows` x1 were the database DDL targets, fixed in the same wave: §5). Tests that run the real TypeSpec compiler (`emission-pipeline`, `all-types-roundtrip`, the DB emitter files) carry explicit timeouts; anything with `tsp` can still be slow when several suites run at once: rerun a failing file alone first. They are not caused by the events work. Repo-wide ESLint has 36 older errors outside the events code (same on `main`).

## 5. Decisions worth challenging

- **Self-contained document** (E1/E2): reuse is by copy; cross-product use is a pinned reference to a *published* event version. No shared Message/Channel catalog.
- **One version per event** (E3), entity pins per message; bump rules at event level (`document/bump.ts`).
- **Keys are generated** (R3); they are real document keys, so renames rewrite references (`renameKey`).
- **Format follows the message** (R4), not the channel; a channel's `format` is only an optional override.
- **Built-in traits are data, not code paths** (MP2): ordinary library traits with an `x-bundled` marker that the services honour; the marker never appears in emitted AsyncAPI.
- **Section naming** (MP1): the section is called "Message properties (Trait)" but also holds operation property sets, grouped. One constant file (`builder/labels.ts`) controls every label.
- **Publish cuts from the saved draft only** and is blocked until every pin (including a library trait's headers entity) is pinned to a published version; the version row is insert-only and freezes the document, the draft, the library traits and the resolved spec, and records the effective payload format of every message (`compatReport.representations`), so a change that only comes from an entity's recorded source format reads as a change (MAJOR) at the next publish.
- **Entity delete is race-free against publish**: the "is it pinned by an event?" guards and the delete run in one transaction under a lock on the entity row (`deleteEntityGuarded` in `src/services/events/entity-pin-usage.ts`, used by both `deleteEntity` and the UI's `deleteEntityAction`); publish takes the same row `FOR SHARE`, so a publish and a delete serialize.
- **No "Source" tab**: the live Code panel is the source view; Versions → View shows a published version's code.
- **External references are pinned to one version and updated manually** — a status line says a newer version exists, nothing changes by itself. An external channel brings no messages of its own: its messages come from the operations that use it.
- **Leave guard**: the browser's Navigation API cannot stop Next's `router.push` (Next renders the new route first and calls `history.pushState` afterwards), so the guard intercepts link clicks and the shell code that navigates asks first through `canNavigate(href)` (`src/lib/navigation/before-navigate.ts`). Back/Forward is cancelled through the Navigation API (Chromium) or a history sentinel elsewhere. **Any new programmatic `router.push` must ask `canNavigate` first** or it will silently skip the guard.
- **Governance for MAJOR publishes is not wired for events** (it never was); `governanceRequestId` stays unused.
- **Squash vs history**: the first big merge to `main` was one squashed commit (no trailer); the cleanup and completion rounds were merged with their individual commits (`--no-ff`); the importer and validation round is merged the same way.
- **Importer creates drafts, never published versions** (2026-10-16): each payload schema becomes a DRAFT entity in the product and its pin stays unpinned. The user publishes the entities and pins the published versions, exactly like a hand-built event; nothing is published on the user's behalf. A document the importers cannot read still imports, with a placeholder entity and a warning.
- **Importer scope** (user decision): paste or upload, AsyncAPI **3.0 only**, no URL fetch, no external `$ref` (the importer has no network access at all). A name clash gets a numeric suffix and a warning rather than a refusal.
- **Retired entities** (user decision, 2026-10-17): publish may still pin a RETIRED entity; no change. **Role gating** (user decision, 2026-10-17): not required now; see gap 6.
- **Validation is advisory**: a schema violation in an example payload, header or binding is a warning in the editor, never a blocker for Save or Publish. The schema library has draft-04 semantics; it is loaded only when a schema exists (a 382 KB chunk, lazy).
- **Bounded input AND a bounded parser** (2026-10-19, replaces "unbounded parser"): everything the importer does BEFORE its first write is bounded by what it is given (1 MiB of text, depth 256, entries per object and per list, expanded size of the document once `$ref`s are replaced, payload and entity counts), and the two steps whose cost cannot be bounded by caps, the AsyncAPI parser and the YAML/JSON read, run in a pool of warm child processes (`src/lib/event-specs/validation/parser-runner.ts`): per-job timeouts (validate 15 s, read 4 s), kill + respawn on timeout, a bounded queue (`PARSER_BUSY` after 20 queued or 30 s of waiting), worker start failures are pool-level (every queued job fails at once, a circuit breaker pauses spawning for 5 s after 3 in a row), fail-closed when the worker file is missing (never a silent in-process fallback), children exit when the server dies. The worker is ONE esbuild-bundled CommonJS file (`worker-dist/asyncapi-parser-worker.cjs`, ~6.9 MiB, no `node_modules` needed) shipped in the standalone output through `outputFileTracingIncludes`; `scripts/verify-parser-worker.mjs` proves it runs from a copy of the standalone output with no repo `node_modules`. Outside production the runner notices an edited source (11 own files, not `node_modules`) and rebuilds once; production never rebuilds.
- **Database DDL targets use their own dialect's decorators** (2026-10-19): the Spanner, PostgreSQL and BigQuery emitter packages are self-contained and read only their own decorators; `db-source.ts` therefore generates sources that import only the dialect package (the shared `@typespec/db` library, whose source was lost in the sibling repo, is no longer used and was removed). This is what the 8 long-standing failures were. Names that cannot become a column are errors that name the field; identifiers and descriptions are escaped (`escapeString`); SQL reserved words, system columns, identifier length limits and dropped letters are WARNINGs (the Schemas tab shows them in one toast).
- **Unknown outcome is never retried blindly**: if the import request is lost after the server may have committed it, the dialog offers Close and refreshes the explorer, not "Try again" (a retry would create the event and every entity a second time).
- **`hasOwnProperty` and `__proto__` are reserved names while we use this AsyncAPI parser** (user decision, 2026-10-19: refuse, do not patch). Cause: `@stoplight/json-ref-resolver` 3.1.6 (inside `@asyncapi/parser` 3.6.4) calls `target.hasOwnProperty(key)` on every object it walks (`crawler.js:35`), so an object with an OWN key of that name crashes the parser; published event versions are insert-only and our documents are read by tools we do not control, so a document the official parser cannot read must never be published. The set lives in ONE place, `PARSER_UNSAFE_KEYS` in `src/lib/event-specs/own-property.ts`, and is enforced by: a guard in `AsyncApiParserValidator.validate` that walks the finished document before the parser (error `PARSER_UNSAFE_KEY` with the JSON pointer, wording for a field, an entity or model name or a plain key); a sanitiser that replaces any parser crash diagnostic by one generic error (no stack trace or server path ever reaches a user); the importer; the builder's key editors and the document parser; entity and model field names (add and rename, the services, TypeSpec source save, bulk importers rename to `X_1` with a warning); and the name registry (entity, enum, scalar, union, API, trait and event names on create and rename). An UNCHANGED legacy name stays editable, the emit guard still blocks publishing it. **To lift it** when the parser (or a fixed copy of that library) no longer crashes on a name: the sweep test goes red and says so; remove the name from `PARSER_UNSAFE_KEYS` and every refusal disappears, then update or delete the tests that pin that name (grep the repo for it; about 20 files hard-code it).
- **Editor patterns are linear by construction** (2026-10-19): JavaScript regexes cannot be time-bounded, so `pinJsonSchemaAction` sends the editor only patterns `isLinearSafePattern` accepts (anchored `^…$`, no quantified group, no backreference or lookaround, at most one unbounded quantifier, at most 1,000 combinations of choices, length ≤ 200, valid with the `u` flag); every other `pattern` (and `patternProperties` key) is removed from the editor's copy of the schema, at any depth including inside `default` / `enum` / `examples` (the schema library follows any JSON pointer). The pattern itself stays in the entity and in the emitted AsyncAPI; the editor just loses an advisory warning. Emails, semver and ranges like `^.{1,2048}$` are not checked in the editor.
- **"Generate from payload" samples a budgeted copy** (`example-from-schema.ts`): our own resolver inlines `$ref`s and merges `if`/`then`/`allOf`/`oneOf`/`anyOf` as the sampler does; every position is charged to a 25,000-unit budget BEFORE it is copied (`required` lists included); scalar keywords are copied only in a closed form (numbers for `min*`/`max*`, text for `format`, text or ≤ 16 texts for `type`, a list of texts for `required`); at most 32 `allOf`/`oneOf`/`anyOf` may be nested inside each other; the example may not exceed 1 MiB. A schema outside this is refused with the generic "Could not generate an example from this schema."

## 6. Known gaps / backlog

1. **AsyncAPI importer and parser — known limitations.** AsyncAPI 3.0 only; no URL fetch; external `$ref` refused; a recursive payload schema becomes a placeholder entity with a warning. The parser is time-bounded (15 s) but a hostile document still OCCUPIES a worker until then: two of them hold both workers (default pool 2) for up to 15 s, during which a normal validation waits (measured 9.6 s behind two 60 channels x 1,999 parameters documents) or answers `PARSER_BUSY` when the queue is full; per-user fairness is not implemented. Each worker is ~160-250 MiB idle and may grow to its 768 MiB heap limit: check container memory (`ASYNCAPI_PARSER_WORKERS`, 1-4). A first validation after a restart costs ~0.5-1 s (worker start); a warm one adds ~10-25 ms. The read step returns JSON, so YAML `.inf`/`.nan`/`-0`/`1e400` become `null`/`0`, `!!binary`/`!!set` become plain objects, a parsed document whose JSON exceeds 8 MiB is refused as `TOO_LARGE`, and answers with more than about 45,000 diagnostics are reported as "too many problems". A worker busy in a long parse when the server is SIGKILLed lingers until the job ends. The expanded-size gate (2 MiB, counted per use of each `$ref` target) is deliberately tight: 50 messages sharing one 10 KB payload schema pass, 100 are refused (the refusal says why). `hasOwnProperty` and `__proto__` are reserved names (see §5).
2. **Infra provider** — only the optional `origin` seam exists; there is no provider registry or sync.
3. **JSON validation — known limitations.** Draft-04 semantics (the library's). Binding schemas are generated from `@asyncapi/specs`; reference cycles are cut with `{}`, so nested levels of a user's JSON Schema inside a binding are not checked and trait bindings have no schema. The Advanced section has no raw-JSON field, so the targets are the example payload/headers and the 24 raw-JSON binding fields. Hover text is shown as plain text (the library's markdown/`innerHTML` rendering of descriptions and messages is switched off in hover, completion and lint, so an image link in a description is never fetched), and the property completion list has no description panel for the same reason. The patterns policy and the sampler's budget are decisions in §5; what they cost: a pattern the editor cannot prove linear is not checked there (the pattern stays in the entity), a `pattern` key inside a `const`/`default`/`examples` object whose text is unsafe loses that key in the editor's copy, a schema with a numeric keyword written as text (`minItems: "3"`) is refused by Generate, and a hand-written conditional whose `if`/`then` brings its own `const`/`enum`/`default`/`allOf` next to its own `oneOf`/`anyOf`/`allOf` is refused with a message naming the construct. The worst wait the nesting cap still allows is under a second (a 32-level `allOf` over a 40,000-key default). The schema of a DRAFT (unpinned) entity is re-rendered by the TypeSpec CLI each time a message card opens (no cache).
4. **External-reference auto-update** — by design manual; there is no notification beyond the status line.
5. **Programmatic navigation** — covered sites: sidebar, command palette, new-entity shortcut, notification centre. Any new call site must use `canNavigate`. In browsers without the Navigation API, Back after a save can need one extra click (history sentinel).
6. **Role gating** — product create / update / delete (and the new Edit contacts) and event publish require a signed-in user of the tenant but do not check the role (`runProductAction` / `runMutation` resolve the role without enforcing it). Entity publish behaves the same. **Decided 2026-10-17: not required for now.**
7. **Sticky Save bar** — it overlays form content while scrolling by design; the clipping reported earlier was not reproducible at maximum scroll. If a focused control ends up under the bar, the fix is `scroll-padding-bottom` on `<main>` in `DashboardClientShell.tsx`.
8. **Copy leftovers** — "trait" still appears in a few problem messages for malformed hand-written documents (`parse-objects.ts`, `resolve.ts`, `event.service.ts`); the pinned-headers note is a literal rather than a `labels.ts` constant.
9. **Retire vs publish.** Publish ignores an entity's status, so a draft can pin (and publish) a *retired* entity. Nothing dangles. **Decided 2026-10-17: keep it that way**; retire's guard stays non-locking.
10. **Residual races** — publishing an *entity version* (`entity-version.service.ts`) does not lock the entity row, so the same guard-versus-edge window remains for the entity-to-entity reference guard; `deleteEntityGuarded` relies on READ COMMITTED (the default).
11. **Big scopes** — the cross-product delete guard excludes the scope's own events with an `IN` list; past roughly 1,600 events (at ~20 versions each) in ONE product/domain the query would exceed the driver's bind limit and the delete would be refused with a generic database error instead of the actionable message. Paging the scan would remove the limit.
12. **Wording leftovers** — "trait" still appears in the publish dialog blocker for an unpinned library trait (`event-publish-facts.ts`), the product-delete blocker ("1 trait"), the entity delete guard ("used by Trait"), bump reasons and `trait.service`/`name-registry` texts.
13. **Small UX leftovers** — a vetoed notification click that is then confirmed leaves the notification unread; the visible Publish hint shifts the header toolbar when it appears; `UsedByPanel` can say "first 0 references" in a rare truncated-but-empty case; the Publish dialog headline repeats the joined blocker messages above the folded list.

15. **Database DDL targets (Spanner, PostgreSQL, BigQuery) — what they do not do.** The generated DDL was run on PGlite for PostgreSQL only; it was never run on Cloud Spanner or BigQuery. Decimal precision is lost: `decimal(19,4)` is emitted as plain `NUMERIC` (the dialect packages have no precision decorator; the Schemas tab mapping snapshot still says `NUMERIC(10,2)`). NOT ENFORCED` is written after the closing parenthesis with a trailing comma (believed invalid, unverified). An entity or field whose name has no Latin letter or digit is an error naming it, so such an entity fails all three DB targets (and `/api/v1/schemas/[id]/validate` reports `ci.pass: false`).
