# Accessibility tier (axe-core, WCAG 2.1 A and AA)

`tests/e2e/a11y.spec.ts` scans every route of the shell, and the states that matter most (login, register, the new-domain dialog, an entity
page with fields, its Schemas tab, the publish dialog, the command palette, an event page, the shell's 404), with axe-core against the tags
`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, and compares what it finds to a recorded **baseline**, `tests/e2e/a11y-baseline.json`.

- a violation that is **not in the baseline fails** the test, and so do **more** elements of a recorded kind than the baseline says: either the page got worse, or nobody has looked at it yet;
- a baseline entry that **no longer occurs fails** it too, and so do **fewer** elements of a kind than recorded ("lower this count"): the baseline can only shrink, per element.

It is `@regression`, in the `a11y` project (Chromium: the Google Chrome of the machine when there is one, the bundled Chromium in CI), and
the regression tier runs it with the `chromium` project, so the nightly run in CI covers it.

```bash
npm run test:e2e:release -- --tier regression --project a11y --reuse-build -- tests/e2e/a11y.spec.ts   # every state
npm run test:e2e:release -- --tier regression --project a11y --reuse-build -- tests/e2e/a11y.spec.ts --grep "lineage"
```

## What a failure says

```
1 NEW accessibility violation(s) in "route:/lineage" (fix the page; do not add them to the baseline):
  + button-name (critical) x1  button[data-testid="lineage-zoom-in"]
      Buttons must have discernible text: https://dequeuniversity.com/rules/axe/4.11/button-name
      <button data-testid="lineage-zoom-in" class="p-1">
```

Fix the page (an `aria-label`, a visible label, the right element). A fix that removes a violation makes the next run say the opposite, "occur less than
recorded ... lower or remove them": lower the `count` or delete the line in `a11y-baseline.json` (or rewrite it, below) in the same change.

## How a violation is identified

By `(state, rule id, element signature)` and a `count`; the states are `route:<path>` for the page sweep's table (`tests/e2e/fixtures/routes.ts`) and
`page:...`, `dialog:...`, `tab:...`, `overlay:...` for the others (the list is in `a11y.spec.ts`).

The **signature** is read from the element itself in the page (`helpers/axe.ts`): its tag, a stable id, its classes in sorted order, and the
attributes that say what kind of element it is (`data-testid`, `data-slot`, `data-variant`, `role`, `type`). Axe's own selector is not used
because it is the shortest selector that is unique **in that page**: it names ancestors, a domain's slug, a different set of classes whenever the
data of the shared test database differs, and a baseline keyed by it failed on runs that changed nothing (measured: three runs of the same
build, one different set of selectors each). Elements of one kind in one state (the badge of each domain card) are one entry with the **number** of them
(`count`): a fourth unlabeled button next to three known ones fails as new, and fixing one of the three fails until the baseline says two.

**Every logged-in state is scanned as a user of a tenant made for that test** (`home` in the spec: a tenant with a domain, a product and an entity, viewed through the
`active_tenant` cookie). The explorer, the domain grid, the compliance results and the governance dashboard list this and nothing else. Without it a scan under the whole
regression run saw a hundred domains made by the other specs, and the same page had different elements from one run to the next (an explorer label here, a pager there): the
first full run after the baseline was made failed five a11y tests for that reason alone, and showed two real bugs (unnamed pager buttons, an unnamed drift badge), now fixed.

Two exceptions exist in the format, and both carry a reason and are capped (`tests/unit/e2e/a11y-baseline.test.ts` fails on an entry whose reason is not a sentence, and on more
than `MAX_CONDITIONAL_ENTRIES` / `MAX_COUNT_VARIES_ENTRIES` of them): `"conditional": "<why>"` (the element exists only when the shared database holds data that no test of
this spec makes: its absence is not a shrink) and `"countVaries": "<why>"` (each is a row of a list that the shared database fills, so only its presence is compared). They are set by hand
and kept by every rewrite. **There are none today**: the one that existed (the Deployments list's "Unknown" version badge) went away with the contrast fix below.

A scan waits first for a quiet page (`waitForQuietPage`): 30 animation frames in a row with no DOM mutation and no `fetch` in flight (the
spec counts them from the first line of every page), fonts loaded, finite animations finished. The browser's colour scheme is light and its motion reduced, and the app
shows its own default theme, **dark** (`src/lib/theme.tsx`): the dark theme is what is scanned (the light one, `/admin/settings`, has other colours: a scan of it is the next step). Nothing is slept.

**What is not scanned:** an `<iframe>`. The scan reads the page's own document (`iframes: false`), so the AsyncAPI preview, which is an iframe, is out of it: its content is
generated by the `@asyncapi/react-component` and has its own accessibility, which this suite does not measure. Axe's "needs review" results (`incomplete`) are not findings either.

## Rewriting the baseline

```bash
UPDATE_A11Y_BASELINE=1 npm run test:e2e:release -- --tier regression --project a11y --reuse-build -- tests/e2e/a11y.spec.ts
```

`UPDATE_A11Y_BASELINE=1` replaces the entries of the states that ran with what the scan finds, counts included (the tests then run one after the other, one writer),
and writes what axe saw, with the element's HTML and the colours and ratio axe measured, to `test-results/a11y-observed/<state>.json` (not committed).
**It is refused whenever `CI` is set** (the spec throws before a test runs, and `assertUpdateAllowed` is unit tested): a pipeline can never accept its own violations. Review
the diff of the file like code: it must only get shorter, and a longer one needs a reason in the commit message (a new page, a new state).
`tests/unit/e2e/a11y-baseline.test.ts` pins the format (sorted, no duplicates, every target a signature, every entry a count, no generated ids).

## Dependency

The scan is `axe-core` (4.11.2, a `devDependency`) driven by `tests/e2e/helpers/axe.ts`, which does what `@axe-core/playwright` does in
a few lines. The package itself was not installed: the registry configured for this repository answered 403 to every package (the saved
token had expired), and axe-core was already in `node_modules` (via `eslint-config-next`). Moving to `@axe-core/playwright` later changes
`scanPage` only; the baseline keys do not depend on it.

## What is left in the baseline, and why

**1 entry, 2 elements** (from 156 findings): `route:/admin/classifications`, `color-contrast` on the colour chips of the PII (`#DC2626` on its 12% tint, 3.49:1) and INTERNAL
(`#2563EB`, 3.19:1) classification levels. Each level carries its own brand colour as data (`SYSTEM_CLASSIFICATION_DEFAULTS`), and the chip draws the text in that colour on a
tint of it: there is no token to lighten, and a pair that passes in the dark theme is a decision for each level's colour (a lighter one in the dark theme, or a darker text on the tint).

To shrink it: choose the dark-theme colour of those two levels, lower the `count` (or remove the entry) in the same change, and the next scan confirms it.
