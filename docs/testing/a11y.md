# Accessibility tier (axe-core, WCAG 2.1 A and AA)

`tests/e2e/a11y.spec.ts` scans every route of the shell, and the states that matter most (login, register, the new-domain dialog, an entity
page with fields, its Schemas tab, the publish dialog, the command palette, an event page, the shell's 404), with axe-core against the tags
`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, and compares what it finds to a recorded **baseline**, `tests/e2e/a11y-baseline.json`.

- a violation that is **not in the baseline fails** the test: either the page got worse, or nobody has looked at it yet;
- a baseline entry that **no longer occurs fails** it too ("remove this entry"): the baseline can only shrink.

It is `@regression`, in the `a11y` project (Chromium: the Google Chrome of the machine when there is one, the bundled Chromium in CI), and
the regression tier runs it with the `chromium` project, so the nightly run in CI covers it.

```bash
npm run test:e2e:release -- --tier regression --project a11y --reuse-build -- tests/e2e/a11y.spec.ts   # every state
npm run test:e2e:release -- --tier regression --project a11y --reuse-build -- tests/e2e/a11y.spec.ts --grep "lineage"
```

## What a failure says

```
1 NEW accessibility violation(s) in "route:/lineage" (fix the page; do not add them to the baseline):
  + button-name (critical)  button[data-testid="lineage-zoom-in"]
      Buttons must have discernible text: https://dequeuniversity.com/rules/axe/4.11/button-name
      <button data-testid="lineage-zoom-in" class="p-1">
```

Fix the page (an `aria-label`, a visible label, the right element). A fix that removes a violation makes the next run say the opposite, "no
longer occur ... remove them": delete those lines from `a11y-baseline.json` (or rewrite it, below) in the same change.

## How a violation is identified

By `(state, rule id, element signature)`; the states are `route:<path>` for the page sweep's table (`tests/e2e/fixtures/routes.ts`) and
`page:...`, `dialog:...`, `tab:...`, `overlay:...` for the others (the list is in `a11y.spec.ts`).

The **signature** is read from the element itself in the page (`helpers/axe.ts`): its tag, a stable id, its classes in sorted order, and the
attributes that say what kind of element it is (`data-testid`, `data-slot`, `data-variant`, `role`, `type`). Axe's own selector is not used
because it is the shortest selector that is unique **in that page**: it names ancestors, a domain's slug, a different set of classes whenever the
data of the shared test database differs, and a baseline keyed by it failed on runs that changed nothing (measured: three runs of the same
build, one different set of selectors each). One consequence: two elements of one kind in one state (the badge of each domain card) are one
entry; fixing one of them does not remove it, fixing all of them does.

**Every logged-in state is scanned as a user of a tenant made for that test** (`home` in the spec: a tenant with a domain, a product and an entity, viewed through the
`active_tenant` cookie). The explorer, the domain grid, the compliance results and the governance dashboard list this and nothing else. Without it a scan under the whole
regression run saw a hundred domains made by the other specs, and the same page had different elements from one run to the next (an explorer label here, a pager there): the
first full run after the baseline was made failed five a11y tests for that reason alone.

A baseline entry can be `"conditional": true`: the element exists only when the shared database holds data that no test of this spec makes (the Deployments list has rows only when
another spec has made a deployment: its "Unknown" version badge). A scan that does not find it is not a shrink, a rewrite keeps it, and the same violation, found, is not new. It is set
by hand and is the exception: there is one.

A scan waits first for a quiet page (`waitForQuietPage`): 30 animation frames in a row with no DOM mutation and no `fetch` in flight (the
spec counts them from the first line of every page), fonts loaded, finite animations finished. The browser's colour scheme is light and its motion reduced, and the app
shows its own default theme, **dark** (`src/lib/theme.tsx`): the dark theme is what is scanned (the light one, `/admin/settings`, has other colours: a scan of it is the next step). Nothing is slept.

## Rewriting the baseline

```bash
UPDATE_A11Y_BASELINE=1 npm run test:e2e:release -- --tier regression --project a11y --reuse-build -- tests/e2e/a11y.spec.ts
```

`UPDATE_A11Y_BASELINE=1` replaces the entries of the states that ran with what the scan finds (the tests then run one after the other, one writer),
and writes what axe saw, with the element's HTML, to `test-results/a11y-observed/<state>.json` (not committed). **CI never sets it.** Review
the diff of the file like code: it must only get shorter, and a longer one needs a reason in the commit message (a new page, a new state).
`tests/unit/e2e/a11y-baseline.test.ts` pins the format (sorted, no duplicates, every target a signature, no generated ids).

## Dependency

The scan is `axe-core` (4.11.2, a `devDependency`) driven by `tests/e2e/helpers/axe.ts`, which does what `@axe-core/playwright` does in
a few lines. The package itself was not installed: the registry configured for this repository answered 403 to every package (the saved
token had expired), and axe-core was already in `node_modules` (via `eslint-config-next`). Moving to `@axe-core/playwright` later changes
`scanPage` only; the baseline keys do not depend on it.

## What was fixed

Found by the first scan (156 findings in 25 states) and fixed, each now held by a unit test or by the baseline itself:

| Rule | Where | Fix |
| --- | --- | --- |
| `link-name` (7 icon-only links on every page) | `ActivityBar` | `aria-label` from the tooltip's text, `aria-current="page"` on the current one, the `nav` named "Main navigation" (`tests/unit/components/shell-accessible-names.test.tsx`) |
| `button-name` (the close button of the right panel, on every page) | `RightPanel` | `aria-label="Close panel"` (same test) |
| `button-name` (Language select) | `SettingsPanel` | `aria-label` |
| `select-name` (three field filters) | `field-editor.tsx` | `aria-label="Filter by type / classification / completeness"` |
| `scrollable-region-focusable` (three scroll areas) | `ComplianceResultsTable`, `GlossaryBrowser`, `TypeSpecPreview` | `tabIndex={0}`, `role="region"`, an `aria-label` |
| `aria-prohibited-attr` (the explorer's loading skeleton, seen when the scan ran before the list had loaded) | `LeftSidebar` | `role="status"`, `aria-busy`, with its label |
| `color-contrast` (the explorer's "N domains") | `LeftSidebar` | the full `text-muted-foreground` instead of its 70% |

## What is left in the baseline, and why

59 entries in 22 kinds, 58 of them `color-contrast` (and one `conditional`: below):

| Group | Entries | Why it is still there | To shrink it |
| --- | --- | --- | --- |
| Muted text on a muted surface: the top bar's "Search or press Ctrl+K..." hint (every page), the explorer's tree labels (`text-[11px] truncate`), the Gaps / Audit Trail tab buttons | 31 | the colour is a design token of the dark theme (`--muted-foreground` `#8a8694` on `--muted` `#2a2a36`, about 3.9:1) that axe measures under 4.5:1 for 11 to 14 px text; changing the token changes the look of every page | darken `--muted-foreground` (or use `text-foreground/70` where it is the hint) and rewrite the baseline: the one hint removes 25 entries |
| Text with an opacity on the colour: `text-muted-foreground/40`, `/50`, `/60`, `/70` (the line numbers of the code view, "Add owner", "+ Add description", "No retention policy", an empty-state line, the 10 px section title) | 12 | placeholder-looking text made faint on purpose | use the plain token where the text has to be read |
| Badges and chips on `bg-muted` / `bg-muted/60` / `bg-primary/10` / the classification colours (`PII`, `INTERNAL`), the secondary badge | 15 | each is a small label (10 to 12 px) whose colours are set one by one | give the badge variants a pair that passes (`badge-pii`, the secondary badge, the chips of the explorer and the field cards) |
| `nested-interactive`: the field cards of the field editor | 1 | the card is `role="button"` (dnd-kit's `useSortable` attributes) and holds buttons and inputs; a screen reader cannot reach the inner controls reliably | move the drag attributes to a handle button inside the card |

The count per rule and per state is in the file itself (`violations`, one per line, with the element's opening tag as `element`).
