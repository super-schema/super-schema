# Known defects

Defects of the product that the browser suite (`tests/e2e`, see `e2e.md`) found and that are not fixed. One entry each, with an id
(`KD-nnn`) that the tests and the commits cite. `tests/unit/e2e-suite-guard.test.ts` reads this file:

- a test that is **expected to fail** (`test.fail`) or hidden (`test.fixme`, a declarative `test.skip`) carries `[KD-nnn what is broken]`
  in its title, and the id must be an entry here. The marker counts wherever it sits (in a `test.step`, in a callback); a whole group
  hidden with `test.describe.skip` / `test.describe.fixme`, and a marker in a hook or directly in a `test.describe`, names the id in the
  title of the group;
- a heading that names a defect must be exactly `## KD-nnn: title` (three digits, one space after the colon): a malformed one fails the
  guard instead of being skipped;
- every entry has a line `- status: open | no-test | dead-code`. An `open` entry is pinned by at least one such test (when the defect is
  fixed, the test passes, which Playwright reports as a failure: delete the `test.fail` line and the entry together). `no-test` says in
  so many words that nothing in the suite pins it (a gap in the product that is not worth a test that fails every night, a design
  limit, a cosmetic one); `dead-code` is code nothing reaches.

An entry gives: what a user sees, how to see it, where it is, the suspected cause, and what fixing it costs.

## KD-001: a per-field type override is recorded but not applied by the generated schema

- status: no-test (the page no longer offers it: nothing can be done to see it)
- symptom: on the Schemas tab, "Manual Override" let a user choose a column type (`STRING(36)` for `id` in BigQuery). The override was
  saved, the toast said "Override applied — schema regenerated", the row said "overridden", and the DDL that came out was the same
  as before (`id STRING NOT NULL`).
- repro (before the table was hidden): generate BigQuery DDL for an entity with a string key, open Manual Override, pick `STRING(36)` for the key.
- where: `saveSchemaFieldTypeOverrideAction` (`src/app/(dashboard)/schemas/[domainSlug]/[productSlug]/[entityId]/actions.ts`) stores
  `metadata.schemaTargetTypeOverrides` and regenerates; every target is generated by the TypeSpec CLI emitters
  (`src/lib/typespec-official`), and nothing there reads the overrides.
- state now: `supportsFieldOverrides` is false for every target (`src/lib/schema-targets/catalog.ts`), so the Manual Override table is
  not offered (`SchemasTab.tsx`) and the Alerts tab raises no "uses persisted field overrides" card for a stored override
  (`generateTargetDriftAlerts`). Stored overrides stay in the data, untouched. `tests/unit/lib/schema-targets/catalog-field-overrides.test.ts`
  pins the flag, and fails when the emitters start to read overrides while no target says so.
- cost to fix: make the emitters take the overrides (a decorator in the generated TypeSpec source, or a post-pass over the emitted
  DDL per dialect), then set the flag for the targets that apply them; the table and the alerts come back with it.

## KD-003: the Versions tab has no diff between versions for entities published in the app

- status: no-test (a product gap, not a malfunction)
- symptom: the Versions tab lists the published versions (label, kind INITIAL / MINOR / MAJOR, summary, who, when). The only place the
  app says WHAT changed is the Publish dialog before a publish (its reasons: `Added optional (nullable) field "memo" — safe
  addition`). "Legacy history" with its "View Diff" is empty for any entity published through the app.
- where: `entity-workspace.tsx` (the "Legacy history (read-only)" block): `src/services/version-history/version.service.ts` reads
  `metadata.versionHistory`, which "nothing writes any more" (Draft + Publish replaced it); the Change Log lists audit entries, and
  the entry of a publish carries no field diff.
- cost to fix: a diff view between two `entity_versions` rows (`fieldSnapshot` is stored on each: `computeDiffResult` already compares two snapshots).

## KD-011: the canonical TypeSpec source of an entity cannot carry a decimal's precision and scale

- status: no-test (a limit of the source format: the field row keeps the precision and scale, a Save of the TypeSpec tab leaves them alone while the field stays a decimal; when the type is edited to a non-decimal the pair is cleared with it)
- symptom: a decimal imported as `NUMERIC(12, 2)` is `decimal` in the entity's TypeSpec source; the DDL targets name the declared
  precision in the table comment (`total: declared decimal(12,2); ...`) because the row has it. A document produced from the source
  alone (a Git export of it) has no precision.
- where: `typespec-generator.ts` / `typespec-parser.ts` have no spelling for it; `merge-fields.ts` does not touch the `precision` / `scale` columns.

## KD-013: the Type Mapping Reference has no row for OpenAPI 3, JSON Schema and the Java POJO

- status: no-test (a design question: the page tabulates "the technologies that have a mapping table", and these have none under their catalog key; `type-mappings.spec.ts` CHARACTERIZES it: the first test lists exactly the five technologies, so the day the table gains a row that test fails and is edited with this entry)
- symptom: `/schemas/type-mappings` has five rows (BigQuery, Avro, Spanner, PostgreSQL, Protobuf) while the Schemas tab offers eight targets. The
  OpenAPI mappings exist (31 entries in `default-mappings.ts`) under the format name `openapi`, and the catalog's key for the target is
  `openapi3`, so the page's filter (`getMappingsForTarget(target.key)`) never finds them. JSON Schema and the Java POJO have no mapping table
  at all.
- where: `src/app/(dashboard)/schemas/type-mappings/type-mapping-reference.tsx` (`TARGETS`), `src/lib/type-mapping/default-mappings.ts`,
  `src/lib/schema-targets/catalog.ts`.
- cost to fix: map the catalog key to the mapping format (`openapi3` -> `openapi`), and write the JSON Schema and Java tables (or say on the page
  that the target has none).

## KD-014: the Classifications tab keeps its levels in page state

- status: open
- symptom: Admin > Classifications lists four levels (PII, SENSITIVE, INTERNAL, PUBLIC) from constants. "Add Classification" adds a level to the
  page, and a reload removes it: nothing is saved. The Edit and Delete buttons do nothing. The levels the field editor, the compliance filters
  and the glossary offer are fixed lists in their own components, so a level made here would reach none of them.
- where: `src/components/custom/admin/ClassificationList.tsx` (`useState(SYSTEM_CLASSIFICATION_DEFAULTS...)`). The persisted side exists and is

  same list (the larger part: each has the four names in code, and `PolicyTemplateSchema` enumerates them).

## KD-016: the compliance Audit Trail reads the audit rows of every tenant

- status: no-test (the Query and Gaps tabs were scoped to the tenant being viewed, the "compliance tenants" test in `governance-compliance.spec.ts` pins it; the Audit Trail cannot be, see below, and no test can say what the right answer is until it has a tenant)
- symptom: the Audit Trail tab lists, and its CSV exports, the `audit_log` rows of ALL tenants: who changed what, in entities, domains and products
  of another tenant. (Before this was fixed the Query and Gaps tabs read every tenant's fields too: `resolveContext` now passes the tenant being

- where: `src/services/compliance.service.ts` (`queryAuditTrail`): `audit_log` has no tenant column; a row names an `entityType` and an `entityId`,

## KD-022: nothing produces a governance request

- status: dead-code
- symptom: `governance.service.createRequest` (the producer: it classifies a change and writes a PENDING or AUTO_APPROVED request) has no caller,
  and neither has `checkEmissionGate` (the check that would stop an emission while a request about the entity is pending): no emission is ever gated.
  The Governance dashboard, its approve and reject and the Admin health card "Pending Governance" read requests that only a database write can

## KD-024: no caller can create a webhook endpoint through the REST API

- status: open
- symptom: `POST /api/v1/webhooks` answers 403 to a session (a session is a VIEWER on this API, KD-025) and 500 `INTERNAL_ERROR` to the API key: the
  key's principal is the user id `api-key-user`, which is no row of `users`, and `webhook_endpoints.createdBy` is a foreign key to `users`, so the
  insert throws. Webhook endpoints that exist can be listed, changed and deleted by the key (the specs write the row); nothing can make one.
- where: `src/app/api/v1/middleware.ts` (`authenticateWithApiKey`: `userId: "api-key-user"`), `src/services/webhook.service.ts` (`createEndpoint`:
  `createdBy: ctx.userId`), `prisma/schema.prisma` (`WebhookEndpoint.creator`).
- pinned by: `api-v1.spec.ts`, "a key creates an endpoint".
- cost to fix: decide who the API key acts as (a real service user row, or `createdBy` optional with a migration), and give a session its real role (KD-025)
  so an admin can create one from the app's own login; then delete the pin.

## KD-025: a session is a viewer on the REST API, the admin's own login included

- status: no-test (a policy of the API that the access-control work will change; `api-v1.spec.ts` CHARACTERIZES it: its test says the admin's session is
  refused by each of the five webhook endpoints, so the day a session gets its real role that test fails and is edited with this entry)
- symptom: `authenticateRequest` gives a session `userRole: "VIEWER"` whoever signed in. The webhook endpoints are for ADMIN only, so a browser session
  gets 403 on them; only the API key (an ADMIN) can use them. Registration is open, so a stranger's session is as much a VIEWER as the seeded admin's.
- where: `src/app/api/v1/middleware.ts` (`authenticateWithSession`).
- cost to fix: resolve the user's effective role (`rbac.service.ts`) there, with tenant- and domain-scoped roles; this is the access-control work.

## KD-026: the schemas routes are not tenant scoped

- status: no-test (a policy the user will change with access control; `api-v1.spec.ts` CHARACTERIZES it: an entity of another tenant is listed by
  `GET /api/v1/schemas` and returned by `GET /api/v1/schemas/:id` to a session that views the default tenant, so a fix edits that test with this entry)
- symptom: `GET /api/v1/schemas` lists the entities of every tenant, `GET /api/v1/schemas/:id`, `/emit` and `/validate` accept the id of any tenant's
  entity (the emission keeps its reference closure inside the entity's own tenant, so a foreign entity is emitted, not mixed with the caller's). The
  detail answer carries `tenantId`, `ownerId` and the whole row. The event-spec route, by contrast, is scoped (a foreign id is the same 404 as an unknown one).
- where: `src/services/entity.service.ts` (`getEntities`, `getEntityById`: no tenant in the query), the four routes under `src/app/api/v1/schemas`.
- cost to fix: the caller's tenant (a session's active tenant, the key's configured one) in `getEntities` / `getEntityById`, as `getActiveTenantId` does for event specs.

## KD-027: the webhook list returns every endpoint's signing secret, and the URL has no policy

- status: no-test (a security note, not something a test can call wrong: `api-v1.spec.ts` shows the list's fields, secret included)
- symptom: `GET /api/v1/webhooks` carries `secret` (the HMAC key of `X-Webhook-Signature`) of every endpoint, on every call, to any ADMIN caller; the
  creation answer is the only one that would need it once. The endpoint URL is any URL that `z.string().url()` accepts: `http://127.0.0.1:5432`,
  a cloud metadata address and `file:` URLs are all accepted, and `dispatchEvent` then makes the server `fetch` it (a server-side request forgery
  surface for whoever holds the API key). Endpoints are global: they belong to no tenant and no user.
- where: `src/services/webhook.service.ts` (`toWebhookEndpoint`, `CreateWebhookEndpointInputSchema` in `src/types/schemas/webhook.ts`, `sendWebhookRequest`).
- cost to fix: leave `secret` out of everything but the creation answer; allow `https:` only (and `http:` for a configured allow-list), refuse private and
  link-local addresses at the time of the request, not only of the URL's text.

## KD-028: the rate limit is keyed by a header the client sends, and its answer has an envelope of its own

- status: no-test (`api-v1.spec.ts` CHARACTERIZES both in its rate-limit test: 429 with `{ error, message, retryAfter }`, and a second `X-Forwarded-For` has its own allowance)
- symptom: `emit`, `validate` and `event-specs` allow 100 requests a minute per client address, read from `X-Forwarded-For` (then `X-Real-IP`), which a caller
  that does not sit behind a proxy that overwrites it can set to anything: another value is another client. The other routes have no limit. The 429
  body is `{ error: "Too Many Requests", message, retryAfter }`, while every other API answer is `{ success: false, error: { code, message } }`; the
  app's own JSON endpoints (`/api/tenants` ...) answer 401 as `{ error: "Not authenticated" }`, a third shape. The limiter is in memory, per process.
- where: `src/app/api/v1/rate-limit.ts`, `src/middleware.ts`.
- cost to fix: take the address from the platform (the connection, or a trusted-proxy count), give the 429 the standard envelope, and a shared store when there is
  more than one instance.
