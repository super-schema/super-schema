# Known defects

Defects of the product that the browser suite (`tests/e2e`, see `e2e.md`) found and that are not fixed. One entry each, with an id
(`KD-nnn`) that the tests and the commits cite. `tests/unit/e2e-suite-guard.test.ts` reads this file:

- a test that is **expected to fail** (`test.fail`) or hidden (`test.fixme`, a declarative `test.skip`) carries `[KD-nnn what is broken]`
  in its title, and the id must be an entry here. The marker counts wherever it sits (in a `test.step`, in a callback); a whole group
  hidden with `test.describe.skip` / `test.describe.fixme`, and a marker in a hook or directly in a `test.describe`, names the id in the
  title of the group;
- a heading that names a defect must be exactly `## KD-nnn: title` (three digits, one space after the colon): a malformed one fails the
  guard instead of being skipped;
- every entry has a line `- status: open | no-test | dead-code`. An `open` entry is pinned by at least one such test (when the defect is
  fixed, the test passes, which Playwright reports as a failure: delete the `test.fail` line and the entry together). `no-test` says in
  so many words that nothing in the suite pins it (a gap in the product that is not worth a test that fails every night, a design
  limit, a cosmetic one); `dead-code` is code nothing reaches.

A pin must fail ONLY on its stated assertion. A bare `test.fail()` at the top of a test passes (as the expected failure) for any reason: a missing fixture, a server that did not
answer, a page that was slow. So the preconditions of a pin (the API key is accepted, the 25 rows are rendered) run FIRST, and `test.fail()` is called after them, immediately
before the one assertion that is the defect (`api-v1.spec.ts`, KD-024; `discovery.spec.ts`, KD-019). The marker still belongs to the title of its test, which the guard reads.

An entry gives: what a user sees, how to see it, where it is, the suspected cause, and what fixing it costs.

## KD-001: a per-field type override is recorded but not applied by the generated schema

- status: no-test (the page no longer offers it: nothing can be done to see it)
- symptom: on the Schemas tab, "Manual Override" let a user choose a column type (`STRING(36)` for `id` in BigQuery). The override was
  saved, the toast said "Override applied — schema regenerated", the row said "overridden", and the DDL that came out was the same
  as before (`id STRING NOT NULL`).
- repro (before the table was hidden): generate BigQuery DDL for an entity with a string key, open Manual Override, pick `STRING(36)` for the key.
- where: `saveSchemaFieldTypeOverrideAction` (`src/app/(dashboard)/schemas/[domainSlug]/[productSlug]/[entityId]/actions.ts`) stores
  `metadata.schemaTargetTypeOverrides` and regenerates; every target is generated by the TypeSpec CLI emitters
  (`src/lib/typespec-official`), and nothing there reads the overrides.
- state now: `supportsFieldOverrides` is false for every target (`src/lib/schema-targets/catalog.ts`), so the Manual Override table is
  not offered (`SchemasTab.tsx`) and the Alerts tab raises no "uses persisted field overrides" card for a stored override
  (`generateTargetDriftAlerts`). Stored overrides stay in the data, untouched. `tests/unit/lib/schema-targets/catalog-field-overrides.test.ts`
  pins the flag, and fails when the emitters start to read overrides while no target says so.
- cost to fix: make the emitters take the overrides (a decorator in the generated TypeSpec source, or a post-pass over the emitted
  DDL per dialect), then set the flag for the targets that apply them; the table and the alerts come back with it.

## KD-028: the rate limit is keyed by a header the client sends, and its answer has an envelope of its own

## KD-029: a union of entities is not followed by the reference closure

- status: no-test (declared, not a failing test: the JSON Schema matrix's `oneof-union-of-models` REQUIRES the failure on JSON Schema, OpenAPI, Avro and Java (Protobuf types a union as a string, so it does not fail) and fails when it stops, and
  the corpus rule `union-of-entity-references` does the same for four documents; both name this entry)
- symptom: a JSON Schema `oneOf` / `anyOf` of `$ref`s to other entities (`method: { oneOf: [Card, Bank] }`) imports as a union field that holds the member NAMES
  (`type: union`, `unionMembers: ["Card", "Bank"]`), and generating the entity for JSON Schema, OpenAPI, Avro or Java fails with
  `invalid-ref: Unknown identifier Card` (the DDL targets, which store the union as text, generate). An array or a map of references, and a plain reference, work.
- where: `src/lib/references/closure.ts` (the walk follows `reference`, array-of-reference and map-of-reference fields; `holdsEntityReference`),
  `src/lib/compiler/closure-source.ts` (a union's members are written by their bare names).
- cost to fix: follow the union members that name entities of the tenant (they hold no id or qualified name, so a bare name two entities share could not be
  picked: the pick action writes one reference to one field, a union needs one per member), write them qualified in the closure source, and give the pick a member.
- note: the multi-entity design names "a field typed `reference`, or an array/map of references" as what is followed; the union was never in it. The goal "every reference
  case of the corpus that fails with `invalid-ref` passes" is met for all but these four documents and the missing-entity cases (KD-031).
