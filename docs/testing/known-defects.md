# Known defects

Defects of the product that the browser suite (`tests/e2e`, see `e2e.md`) found and that are not fixed. One entry each, with an id
(`KD-nnn`) that the tests and the commits cite. `tests/unit/e2e-suite-guard.test.ts` reads this file:

- a test that is **expected to fail** (`test.fail`) or hidden (`test.fixme`, a declarative `test.skip`) carries `[KD-nnn what is broken]`
  in its title, and the id must be an entry here. The marker counts wherever it sits (in a `test.step`, in a callback); a whole group
  hidden with `test.describe.skip` / `test.describe.fixme`, and a marker in a hook or directly in a `test.describe`, names the id in the
  title of the group;
- a heading that names a defect must be exactly `## KD-nnn: title` (three digits, one space after the colon): a malformed one fails the
  guard instead of being skipped;
- every entry has a line `- status: open | no-test | dead-code`. An `open` entry is pinned by at least one such test (when the defect is
  fixed, the test passes, which Playwright reports as a failure: delete the `test.fail` line and the entry together). `no-test` says in
  so many words that nothing in the suite pins it (a gap in the product that is not worth a test that fails every night, a design
  limit, a cosmetic one); `dead-code` is code nothing reaches.

An entry gives: what a user sees, how to see it, where it is, the suspected cause, and what fixing it costs.

## KD-001: a per-field type override is recorded but not applied by the generated schema

- status: no-test (the page no longer offers it: nothing can be done to see it)
- symptom: on the Schemas tab, "Manual Override" let a user choose a column type (`STRING(36)` for `id` in BigQuery). The override was
  saved, the toast said "Override applied — schema regenerated", the row said "overridden", and the DDL that came out was the same
  as before (`id STRING NOT NULL`).
- repro (before the table was hidden): generate BigQuery DDL for an entity with a string key, open Manual Override, pick `STRING(36)` for the key.
- where: `saveSchemaFieldTypeOverrideAction` (`src/app/(dashboard)/schemas/[domainSlug]/[productSlug]/[entityId]/actions.ts`) stores
  `metadata.schemaTargetTypeOverrides` and regenerates; every target is generated by the TypeSpec CLI emitters
  (`src/lib/typespec-official`), and nothing there reads the overrides.
- state now: `supportsFieldOverrides` is false for every target (`src/lib/schema-targets/catalog.ts`), so the Manual Override table is
  not offered (`SchemasTab.tsx`) and the Alerts tab raises no "uses persisted field overrides" card for a stored override
  (`generateTargetDriftAlerts`). Stored overrides stay in the data, untouched. `tests/unit/lib/schema-targets/catalog-field-overrides.test.ts`
  pins the flag, and fails when the emitters start to read overrides while no target says so.
- cost to fix: make the emitters take the overrides (a decorator in the generated TypeSpec source, or a post-pass over the emitted
  DDL per dialect), then set the flag for the targets that apply them; the table and the alerts come back with it.

## KD-003: the Versions tab has no diff between versions for entities published in the app

- status: no-test (a product gap, not a malfunction)
- symptom: the Versions tab lists the published versions (label, kind INITIAL / MINOR / MAJOR, summary, who, when). The only place the
  app says WHAT changed is the Publish dialog before a publish (its reasons: `Added optional (nullable) field "memo" — safe
  addition`). "Legacy history" with its "View Diff" is empty for any entity published through the app.
- where: `entity-workspace.tsx` (the "Legacy history (read-only)" block): `src/services/version-history/version.service.ts` reads
  `metadata.versionHistory`, which "nothing writes any more" (Draft + Publish replaced it); the Change Log lists audit entries, and
  the entry of a publish carries no field diff.
- cost to fix: a diff view between two `entity_versions` rows (`fieldSnapshot` is stored on each: `computeDiffResult` already compares two snapshots).

## KD-006: the right panel's TypeSpec editor, opened before the preview has loaded, opens empty

  "Preview Changes" is disabled.

## KD-007: the Change Log shows the raw audit action and the user's id initial

## KD-008: saving an entity's description gives no sign that it was saved

- status: no-test (UX)
- symptom: no toast and no "Saved" flash; a page load straight after the click can still read the old description (the action is

## KD-009: the Java POJO target writes a reference field as a `String`

- status: no-test (a design question: a reference is stored as its key)
- symptom: an OpenAPI schema `Product { price: Money }` imports `price` as a reference to `Money`; the Java POJO has `private String price;`.

## KD-010: in the new-field form Escape closes the form, not the suggestion list

- status: no-test (UX)
- symptom: a field name the autocomplete knows (`amount`) opens a suggestion list over the Quick Create buttons; pressing Escape to
  dismiss it closes the whole form (`field-editor.tsx`'s own Escape shortcut); clicking elsewhere closes the list after 200 ms.

## KD-011: the canonical TypeSpec source of an entity cannot carry a decimal's precision and scale

- status: no-test (a limit of the source format: the field row keeps the precision and scale, a Save of the TypeSpec tab leaves them alone while the field stays a decimal; when the type is edited to a non-decimal the pair is cleared with it)
- symptom: a decimal imported as `NUMERIC(12, 2)` is `decimal` in the entity's TypeSpec source; the DDL targets name the declared
  precision in the table comment (`total: declared decimal(12,2); ...`) because the row has it. A document produced from the source
  alone (a Git export of it) has no precision.
- where: `typespec-generator.ts` / `typespec-parser.ts` have no spelling for it; `merge-fields.ts` does not touch the `precision` / `scale` columns.

## KD-012: the @slow jsonschema matrix is red until multi-entity Task 12 removes its stale entries

- status: no-test (the @slow jsonschema matrix is itself the red signal; it is to be removed, not pinned, by multi-entity Task 12)
- symptom: the nightly (`@slow`) JSON Schema matrix fails. It still lists entries in `MULTI_MODEL_KNOWN` / `knownSync` for cases the
  multi-entity import has since fixed (they now pass where the matrix expects a failure), and it has no expectation yet for the protobuf
  emitter's nested array of an array of references (the output has a nested array where the matrix says nothing).
- where: `tests/e2e/jsonschema-lifecycle.spec.ts` and `tests/e2e/fixtures/jsonschema-variations.ts` (`MULTI_MODEL_KNOWN`, `knownSync`).
- to remove: multi-entity Task 12 drops the stale `MULTI_MODEL_KNOWN` / `knownSync` entries and adds a protobuf nested-array expectation for
  array-of-refs. That task deletes this entry with them.
## KD-013: the Type Mapping Reference has no row for OpenAPI 3, JSON Schema and the Java POJO

- status: no-test (a design question: the page tabulates "the technologies that have a mapping table", and these have none under their catalog key)
- symptom: `/schemas/type-mappings` has five rows (BigQuery, Avro, Spanner, PostgreSQL, Protobuf) while the Schemas tab offers eight targets. The
  OpenAPI mappings exist (31 entries in `default-mappings.ts`) under the format name `openapi`, and the catalog's key for the target is
  `openapi3`, so the page's filter (`getMappingsForTarget(target.key)`) never finds them. JSON Schema and the Java POJO have no mapping table
  at all.
- where: `src/app/(dashboard)/schemas/type-mappings/type-mapping-reference.tsx` (`TARGETS`), `src/lib/type-mapping/default-mappings.ts`,
  `src/lib/schema-targets/catalog.ts`.
- cost to fix: map the catalog key to the mapping format (`openapi3` -> `openapi`), and write the JSON Schema and Java tables (or say on the page
  that the target has none).

## KD-014: the Classifications tab keeps its levels in page state

- status: open
- symptom: Admin > Classifications lists four levels (PII, SENSITIVE, INTERNAL, PUBLIC) from constants. "Add Classification" adds a level to the
  page, and a reload removes it: nothing is saved. The Edit and Delete buttons do nothing. The levels the field editor, the compliance filters
  and the glossary offer are fixed lists in their own components, so a level made here would reach none of them.
- where: `src/components/custom/admin/ClassificationList.tsx` (`useState(SYSTEM_CLASSIFICATION_DEFAULTS...)`). The persisted side exists and is
  not used by the page: `classification-taxonomy.service.ts`, `src/server/api/routers/admin/classifications.ts`, `useAdminClassifications.ts`,
  the seeded `classification_levels` rows.
- pinned by: `admin.spec.ts`, "a level that was added is still listed after a reload".
- cost to fix: server actions over the service for list / create / update / delete, the component reading them, then the pickers reading the
  same list (the larger part: each has the four names in code, and `PolicyTemplateSchema` enumerates them).

## KD-015: a refused governance decision is not explained

- status: open
- symptom: a user who is not a Steward or an Admin presses Approve or Reject and confirms: the request stays pending and the page says nothing.
  The service answers "Only Steward or Admin roles can approve governance requests"; the page drops it.
- where: `src/app/(dashboard)/governance/page.tsx` (`handleApprove` / `handleReject`: `if ("success" in result)` and no else).
- pinned by: `governance-compliance.spec.ts`, "a user who may not decide is told so".
- cost to fix: show the error (a toast, or under the card) and, better, not offer the buttons to a user who cannot use them.

## KD-016: the compliance pages read the fields of every tenant

- status: open
- symptom: the Query tab lists, the Gaps tab counts and the Audit Trail tab lists the rows of ALL tenants (a field of another tenant's entity
  appears in the table of the tenant being viewed). The Lineage Graph and the command palette's fields did the same (the graph is fixed: it reads
  the active tenant; the palette is KD-020).
- where: `src/services/compliance.service.ts` (`queryFields`, `detectGaps`: no tenant in the where clause; `audit_log` has no tenant column).
- pinned by: `governance-compliance.spec.ts`, "an entity of another tenant is not listed".
- cost to fix: the routes take the active tenant (`getActiveTenantId`) and the two queries filter `entity: { tenantId }`; the audit trail needs the
  tenant of the audited row (a join by entity type, or a column).
