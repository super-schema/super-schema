# Known defects

Defects of the product that the browser suite (`tests/e2e`, see `e2e.md`) found and that are not fixed. One entry each, with an id
(`KD-nnn`) that the tests and the commits cite. `tests/unit/e2e-suite-guard.test.ts` reads this file:

- a test that is **expected to fail** (`test.fail`) or hidden (`test.fixme`, a declarative `test.skip`) carries `[KD-nnn what is broken]`
  in its title, and the id must be an entry here. The marker counts wherever it sits (in a `test.step`, in a callback); a whole group
  hidden with `test.describe.skip` / `test.describe.fixme`, and a marker in a hook or directly in a `test.describe`, names the id in the
  title of the group;
- a heading that names a defect must be exactly `## KD-nnn: title` (three digits, one space after the colon): a malformed one fails the
  guard instead of being skipped;
- every entry has a line `- status: open | no-test | dead-code`. An `open` entry is pinned by at least one such test (when the defect is
  fixed, the test passes, which Playwright reports as a failure: delete the `test.fail` line and the entry together). `no-test` says in
  so many words that nothing in the suite pins it (a gap in the product that is not worth a test that fails every night, a design
  limit, a cosmetic one); `dead-code` is code nothing reaches.

A pin must fail ONLY on its stated assertion. A bare `test.fail()` at the top of a test passes (as the expected failure) for any reason: a missing fixture, a server that did not
answer, a page that was slow. So the preconditions of a pin (the API key is accepted, the 25 rows are rendered) run FIRST, and `test.fail()` is called after them, immediately
before the one assertion that is the defect (`discovery.spec.ts`, KD-019). The marker still belongs to the title of its test, which the guard reads.

An entry gives: what a user sees, how to see it, where it is, the suspected cause, and what fixing it costs.

## KD-001: a per-field type override is recorded but not applied by the generated schema

- status: no-test (the page no longer offers it: nothing can be done to see it)
- symptom: on the Schemas tab, "Manual Override" let a user choose a column type (`STRING(36)` for `id` in BigQuery). The override was
  saved, the toast said "Override applied — schema regenerated", the row said "overridden", and the DDL that came out was the same
  as before (`id STRING NOT NULL`).
- repro (before the table was hidden): generate BigQuery DDL for an entity with a string key, open Manual Override, pick `STRING(36)` for the key.
- where: `saveSchemaFieldTypeOverrideAction` (`src/app/(dashboard)/schemas/[domainSlug]/[productSlug]/[entityId]/actions.ts`) stores
  `metadata.schemaTargetTypeOverrides` and regenerates; every target is generated by the TypeSpec CLI emitters
  (`src/lib/typespec-official`), and nothing there reads the overrides.
- state now: `supportsFieldOverrides` is false for every target (`src/lib/schema-targets/catalog.ts`), so the Manual Override table is
  not offered (`SchemasTab.tsx`) and the Alerts tab raises no "uses persisted field overrides" card for a stored override
  (`generateTargetDriftAlerts`). Stored overrides stay in the data, untouched. `tests/unit/lib/schema-targets/catalog-field-overrides.test.ts`
  pins the flag, and fails when the emitters start to read overrides while no target says so.
- cost to fix: make the emitters take the overrides (a decorator in the generated TypeSpec source, or a post-pass over the emitted
  DDL per dialect), then set the flag for the targets that apply them; the table and the alerts come back with it.

## KD-029: a union of entities is not followed by the reference closure

- status: no-test (declared, not a failing test: the JSON Schema matrix's `oneof-union-of-models` REQUIRES the failure on JSON Schema, OpenAPI, Avro and Java (Protobuf types a union as a string, so it does not fail) and fails when it stops, and
  the corpus rule `union-of-entity-references` does the same for four documents; both name this entry)
- symptom: a JSON Schema `oneOf` / `anyOf` of `$ref`s to other entities (`method: { oneOf: [Card, Bank] }`) imports as a union field that holds the member NAMES
  (`type: union`, `unionMembers: ["Card", "Bank"]`), and generating the entity for JSON Schema, OpenAPI, Avro or Java fails with
  `invalid-ref: Unknown identifier Card` (the DDL targets, which store the union as text, generate). An array or a map of references, and a plain reference, work.
- where: `src/lib/references/closure.ts` (the walk follows `reference`, array-of-reference and map-of-reference fields; `holdsEntityReference`),
  `src/lib/compiler/closure-source.ts` (a union's members are written by their bare names).
- cost to fix: follow the union members that name entities of the tenant (they hold no id or qualified name, so a bare name two entities share could not be
  picked: the pick action writes one reference to one field, a union needs one per member), write them qualified in the closure source, and give the pick a member.
- note: the multi-entity design names "a field typed `reference`, or an array/map of references" as what is followed; the union was never in it. The goal "every reference
  case of the corpus that fails with `invalid-ref` passes" is met for all but these four documents and the missing-entity cases (KD-031).

## KD-033: generating or publishing a schema version rewrites the whole `metadata`, which can overwrite a concurrent atomic write

- status: no-test (a race between two requests: the unit tests run one at a time)
- symptom: `generateSchemaAction` and `publishSchemaAction` read `entity.metadata`, change `schemaVersions`, and write the WHOLE object back with `prisma.entity.update`. A write that landed in

## KD-034: the tenant being viewed is a per-browser cookie, a CHOICE among the tenants the user holds a role in

- status: no-test (what is left is a design limit of the switcher, not a boundary: the boundary is the role, and it is unit-tested everywhere the choice is used)
- symptom: the tenant in view is the `active_tenant` cookie (`getActiveTenantId`, `src/lib/active-tenant.ts`), set by the switcher in the browser. It is **no longer a free pick** (access-control Tasks 3, 5, 6): it counts only
  for a tenant the signed-in user holds a role in, at any depth (a platform administrator: any tenant); otherwise the first tenant they can access; a user with no role gets `NoTenantAccess`
  (`/no-access` for a page, 404 or 403 JSON for an API route, never a 500); `setActiveTenantAction` refuses any other tenant exactly as it refuses a missing one, and `/api/tenants` lists only the
  tenants the user may access. What a user may DO and SEE is decided by their roles, at the data layer: every server action asks `authorizeInActiveTenant` (the resource must lie in the tenant in view AND
  a covering role must reach the action: a user with roles in tenants A and B and A in view cannot read or write B's rows by id, a platform administrator included), every `/api/v1` and `/api/*` route asks
  `withApiAuth` (a session carries the user's real roles; the API key is a service principal bound to `API_KEY_TENANT_ID`), and every page and loader that reads the database asks the principal's
  assignments (`requirePageAccess`, `can`, `canListDomain`, `canListProduct`, `readableWhere`) and looks a domain up INSIDE the tenant in view (the tenant-agnostic fallbacks that tolerated a stale cookie are gone).
  `tests/unit/access/deny-by-default.test.ts` fails for a server action or a route handler that is neither guarded nor on the allow-list, and both pending lists are empty.
  What is left: the choice lives in a cookie of one browser, so a user with roles in two tenants who opens a deep link into the tenant that is not in view gets a 404 until they switch (the same answer as a
  missing page, on purpose: it says nothing about what exists), and a cookie that names a tenant whose role was since revoked falls back to the first accessible tenant without telling the user.
  Not a boundary either, and recorded on their own: the glossary is one list for every tenant (KD-043), an event document may name an entity its author may not read (KD-044), and an entity's emission, validation,
  preview, generation and publish used to include the entities it references whether or not the caller could read them (KD-045, fixed): the closure now refuses (`REFERENCE_NOT_READABLE`) when it reaches
  an entity no role of the caller covers, before anything is built from it (`entityReader`, `tests/unit/access/closure-reader-scan.test.ts` keeps every caller honest). The stored result of an earlier
  generation by a wider role carried the files of the entities it referenced (KD-046, fixed): every reader of `metadata.schemaVersions` (the Schemas tab, `getSchemaVersionsAction`, `GET /api/v1/schemas/:id`,
  the entity page, the change log) now gets a copy with the files of entities its roles do not cover removed, `output` rebuilt from the rest (`src/lib/access/schema-version-redaction.ts`;
  `tests/unit/access/schema-versions-scan.test.ts` keeps every reader honest).
- where: `src/lib/active-tenant.ts`, `setActiveTenantAction`, `src/lib/access/api.ts`, `src/lib/access/page-access.ts`, `src/app/api/tenants/route.ts`.
- cost to fix: keep the choice per user on the server (a column on `users`, read by `getActiveTenantId`) and say so on the page that falls back; or show the user the tenant they were sent to.

## KD-041: a string enum of more than 5,000 values is imported with its first 5,000 and a warning, on the shared enum and on every field that names it

## KD-043: the glossary is one list for every tenant

## KD-044: an event document can name an entity or an event its author may not read

- status: no-test (the readers are closed, the saved reference is not)
- symptom: the pin picker, the pinned schema and the external-reference loaders answer only for entities and events the caller's roles cover (access-control Task 5b). Saving an event document whose message pins an

## KD-047: no in-app screen stores the settings of an identity provider (not built)

- status: no-test (a feature that was deliberately not built, not a malfunction: nothing can fail)
- symptom: an administrator can add identity providers to the sign-in (Google, GitHub, Microsoft Entra ID, Okta, Keycloak, a generic OpenID Connect issuer: `docs/auth.md`), but only by setting `AUTH_PROVIDERS` and the
