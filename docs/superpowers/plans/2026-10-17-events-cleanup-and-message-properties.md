# Events — legacy removal, CodeMirror, and "Message properties" (traits redesign)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Each work package (WP) is dispatched to its own agent in its own worktree; the controller merges. **No `Co-Authored-By` trailer or "Generated with" line in any commit** (user rule).

**Context:** `main` (b41c7519) has the new self-contained Event builder. The user reviewed it (2026-10-16/17) and asked for: (1) the legacy Message/Channel/Spec code, tables and tests removed so new work is easy; (2) the npm registry is fixed → use CodeMirror 6 (installed on this branch: `@codemirror/{state,view,commands,language,lang-json,lang-yaml,lint}`, `@lezer/highlight`; `@asyncapi/specs` is now a direct devDependency); (3) worktree cleanup; (4) everything merged back to `main` in a state they can review fully; (5) a rework of how Traits feel — their words below.

## User feedback on Traits (verbatim in substance)

- "Traits in Event is not really well understood, so let's say **Message Properties** instead, and put **(Trait)** in brackets in the details wherever possible."
- "After the CloudEvents trait is added, **where do users set the properties**?"
- "At enterprise level, why is the CloudEvents header registered as an **entity**? It should be a **trait — message properties — which anybody can simply select** when they pick CloudEvents as a message trait, and **show the unmodifiable properties in the UI**. I can see it in the final YAML in the detail panel but it should also be visible on the UI."
- "The UI for each trait or message looks **very crowded**. Adding a trait should be a **simple plus button**; whether it's a message or operation trait should just be a **selection**; then a selection for the type it follows. Let's think about the UI experience."

## Design decisions (Message properties)

| # | Decision |
|---|---|
| MP1 | **Naming.** Everywhere the user sees "Trait(s)" it becomes **Message properties**, with **(Trait)** as the bracketed secondary text (badge "Trait", page subtitle "Message properties (Trait)"). Operation traits read **Operation properties (Trait)**. All labels come from one module `src/features/events/builder/labels.ts` so they can be changed in one place. Covers: builder outline section, the Enterprise/Domain tab and sidebar leaf that list library traits, the create menu entry ("New Message Properties"), page titles, empty states, tooltips, and test ids stay stable (`trait-*`). |
| MP2 | **CloudEvents is a trait, not an entity.** The bundled library trait **CloudEvents 1.0** (tenant level) carries its properties inline as `spec.headers` (a JSON Schema object: `specversion` (const "1.0", required), `id` (required), `source` (uri-reference, required), `type` (required), `subject`, `time` (date-time), `datacontenttype`, `dataschema` (uri)). A second bundled trait **W3C Trace Context** (`traceparent`, `tracestate`). Bundled traits are marked `spec["x-bundled"] = "<id>@<version>"`, are created idempotently for every tenant (`ensureBundledTraits`), and are **read-only**: the trait service refuses update/delete with a clear message and every UI shows a lock and "Built in — can't be modified". The `CloudEventsHeaders` entity is removed from the demo data (events use the trait instead). |
| MP3 | **One "+ Add" flow.** In the Message properties section a single primary **+ Add** opens a popover: *Applies to* **Message \| Operation** (segmented), then a searchable list *Start from*: **Built in** (CloudEvents 1.0 — 8 properties, W3C Trace Context — 2 properties), **Library** (Tenant/Domain traits of that kind), and **New (blank)**. Choosing a built-in or library item adds it immediately and selects it; "New" adds a blank local item and focuses its name. No kind picker form, no key field. |
| MP4 | **Properties are visible where they are used.** The message form gets a **Message properties (Trait)** card: a chip per applied property set (name + "Trait" badge) with **+ Add** (same chooser, filtered to message kind), and each chip expands to a table of its properties (name, type, required, description) — **locked and read-only for built-in/library** ("Defined by CloudEvents 1.0"), editable for local ones. Adding from the message form creates the document entry (auto key) and applies it to the message in one step — no detour. Operations get the same card ("Operation properties (Trait)"). |
| MP5 | **Local property sets use a Properties table** (rows: name, type (text, whole number, decimal, true/false, date-time, link), required, description, allowed values) that generates `spec.headers` JSON Schema. Everything else (title, summary, correlation id, examples, bindings, tags, docs) sits under a collapsed **More details** with a count of what is set. Operation property sets have no schema properties in AsyncAPI, so they show their metadata fields (title, summary, description, tags, docs, security, bindings) with the same collapsed layout. |
| MP6 | **Library trait editor** (Enterprise/Domain "Message properties" tab) uses the same Properties table; built-in ones are read-only; the "headers entity" picker is removed for traits (existing `headersEntityId` rows keep working but are not offered). |
| MP7 | **Less crowded.** The message and operation forms become accordion cards with counts: *Payload* (open), *Message properties (Trait)* (open), *Details* (open: name, title, summary, description, content type), and collapsed: *Examples*, *Bindings*, *Docs & tags*, *Correlation id*, *More*. Field help text becomes a small info tooltip for optional fields (kept inline for required ones). The Message properties section list shows two quiet groups ("On messages", "On operations"). |
| MP8 | **Code panel and Docs** already show the merged trait headers; the instant (client-side) code must now show the real property definitions of library/built-in traits (not a stub), so `BuilderOptions.libraryTraits` carries `spec`, `bundled` and a property summary. |

## Review Focus

1. A tenant with no bundled traits yet (created before this change) must get them on `ensure`; running `ensure` twice must not duplicate or rename.
2. A document that already references the old custom `CloudEvents` library trait (entity-pinned headers) must still open, save and emit — existing trait rows with `headersEntityId` keep working.
3. The guard migration must refuse on a DB with any legacy row and pass on a clean one — both proven in tests; it must never delete user data silently.
4. Removing a property set that messages use must remove its key from every `traitKeys` (existing rule) — also from the message card's chip row.
5. Read-only really means read-only: the service refuses to update/delete a bundled trait even if the UI is bypassed.
