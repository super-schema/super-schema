## Known issues (not defects of this repo)

- `bigquery-pk-after-column-list` [sibling] (bigquery; owner: @typespec/bigquery write.ts:74-77; 247 cases): Sibling emitter defect, confirmed against BigQuery's documented CREATE TABLE grammar and not confirmable on the emulator. The emitter writes `) PRIMARY KEY (...) NOT ENFORCED` AFTER the closing paren of the column list (Spanner's form); BigQuery's grammar takes the constraint inside the element list. The LocalCloud emulator (ZetaSQL parser) rejects the emitted form (`PRIMARY KEY must be defined in the table element list as column attribute or constraint`); moved inside the list it says `Unsupported table DDL fields: ['primaryKey']` (it cannot create primary-key tables at all); without the clause the DDL is accepted. sqlglot accepts both placements, so it is no evidence either way.
- `bigquery-array-not-null` [sibling] (bigquery; owner: @typespec/bigquery write.ts (NOT NULL on a required ARRAY column); 23 cases): A required array field is written `col ARRAY<T> NOT NULL`. The engine's analyzer says `Columns and fields of ARRAY type do not support the NOT NULL modifier` (the message real BigQuery gives: an ARRAY column is never NULL, only empty), so the DDL cannot run. Judged without the primary-key clause so it is not hidden by bigquery-pk-after-column-list.
- `bigquery-emulator-timestamp-array` [emulator] (bigquery; owner: LocalCloud BigQuery emulator; 3 cases): `ARRAY<TIMESTAMP>` is rejected by the emulator's own loader (`TIMESTAMP columns are qualified only as top-level non-repeated columns`); real BigQuery supports arrays of timestamps. Not an emitter or app defect.
- `java-enum-without-package` [sibling] (java-pojo; owner: @typespec/java-pojo write.ts writeJavaEnum; 17 cases): writeJavaEnum writes `public enum X {...}` with no `package` line while the POJO is in `package com.superschema.generated;`, so the class cannot see its enum (javac: cannot find symbol). javac compiles once the package line is added to the enum file (the validator proves it).
- `java-javadoc-not-escaped` [sibling] (java-pojo; owner: @typespec/java-pojo write.ts javadoc(); 2 cases): A description containing `*/` is written into the Javadoc unescaped, closing the comment early: javac `class, interface, enum, or record expected`. Source text of a schema can therefore inject Java code into the generated file.
- `avro-recursive-model-crash` [sibling] (avro; owner: @typespec/avro transform.ts mapType; 2 cases): A model that refers to itself (`children: Node[]`, `parent: Node`) makes the emitter recurse without a visited set: `RangeError: Maximum call stack size exceeded` at mapType (transform.ts:261-270), reported by the app as `The TypeSpec emitter failed.`. Avro supports recursive records by name.
- `multi-model-emission-gap` [open] (json-schema, openapi3, avro, protobuf, java-pojo; owner: this repo (documented gap: default-mappings.ts reference -> protobuf lossDescription); 25 cases): An entity is emitted ALONE (emitOfficialTypeSpecTargetFromData takes one entity), so a field that references another entity of the same document (`$ref: #/$defs/Addr`, a oneOf of refs, a model reference) names a type that is not in the compile unit: `invalid-ref: Unknown identifier X`. Only matched when X is an entity the case's own document defines or refers to. The DB targets store a reference as text and are unaffected.
- `protobuf-nested-array` [official] (protobuf; owner: @typespec/protobuf; 1 cases): `@typespec/protobuf/nested-array: nested arrays are not supported by the Protobuf emitter`: protobuf cannot express repeated repeated fields; the app does not project an array of arrays for this target (the DB targets note `declared array; stored as ARRAY<...>`).
- `name-collision-guard` [by-design] (avro, protobuf, java-pojo; owner: this repo name-collisions.ts (refusal); 4 cases): Names that the target writes as the same identifier (`a-b` / `a_b`, `😀` / `名前`) are refused before emitting with a message naming both and the identifier (the DB targets do the same in db-source.ts).
- `name-too-long-guard` [by-design] (all targets; owner: this repo emitter.service.ts (refusal); 2 cases): A stored entity / field name over 128 characters (a TypeSpec import or a hand-built entity bypasses the JSON Schema import limit) is refused at generation with a message naming it, instead of crashing the emitters with ENAMETOOLONG.
- `db-name-guard` [by-design] (postgresql, spanner, bigquery; owner: this repo db-source.ts (refusal); 2 cases): A name that cannot become a column name, or that collides with another after normalisation, is refused with an actionable message naming the fields (`cannot be turned into a column name`, `would all become the column`).
- `openapi-internal-ref-extension` [open] (openapi3; owner: this repo importer (additionalProperties kept verbatim as an extension, by design); 3 cases): `additionalProperties` is not mapped by the importer (IGNORED_SCHEMA_KEYWORDS) and is kept verbatim as an extension so a JSON Schema round trip loses nothing. When its value is a `$ref: #/$defs/V` the OpenAPI document gets `additionalProperties: {$ref: '#/$defs/V'}`, which does not resolve there. Only matched when the unresolved pointer is one the case's own source contains.
